LLM4L5X: every folder and file, with what it is.
Made by `python -m eval.structure` from the folders' README.md and the files' docstrings;
a test fails when this file is out of date. Edit those, then run the command again.

core/                      The engine everything else stands on: LogicSpec, the compiler, rung text, the scan simulator, UDT memory layout.
  __init__.py
  ascii.py                 ASCII rung text <-> neutral text.
  catalog.py               Instruction catalog: loads instructions.yaml and lets L5X content extend it (AOIs).
  compiler.py              Compile LogicSpec into ladder rungs.
  describe.py              Deterministic English read-back of LogicSpec.
  instructions.yaml
  logicspec.py             LogicSpec: the small boolean language the LLM writes instead of rung text.
  README.md
  rung.py                  Ladder neutral text: AST, parser and printer.
  rung_compare.py          Do two sets of rungs behave the same?
  simulator.py             A small Logix scan simulator for testing compiled rungs.
  udt_layout.py            UDT memory layout: byte size as Studio 5000 lays it out, and the member order that wastes no padding.
  validator.py             Import checks on rungs, independent of where they came from (model, compiler, project): syntax, operand count and types, tags that exist, instruction names for the target version.
devices/                   Device models: what the field devices do when the program drives them (pumps, motors, valves), so a program can run without the machine.
  __init__.py              Device models: what the field devices do when the PLC drives them.
  devices.py               Device models: motor/pump with or without run feedback, 2-position valve (single or double solenoid, 0, 1 or 2 limit switches).
  plant.py                 A plant: a set of devices stepped together, loaded from YAML, with PLANT: tags for tests.
  README.md
docs/
  DESIGN.md                How it works inside, and why
  DEVELOPMENT.md           For developers: layout, tests, the instruction suite
  DEVICES.md               A plant model plays the field devices: it reads the PLC's command tags and writes the feedback a real device would give, after the time a real device takes.
  GUIDE.md                 For users: every feature in detail
  HANDOVER.md              Start here when picking the work up: map of the code, working rules, results
  IOLIST.md                `generate/iolist.py` reads an Excel I/O list.
  LIBRARY.md               A block is one YAML file that gives a device everything at once: rungs, tag types, a plant model and scenario tests.
  PROFILE.md               A YAML file with the rules that differ per company.
  ROADMAP.md               What is done and what is next
  TESTCASES.md             Requirement-level tests for the logic, with a plant model, in OpenVnV's step language.
eval/                      Measuring quality, for developers: the model's scores, the always-correct oracle run, the instruction suite, the public corpus, and this repository's map.
  __init__.py
  corpus_sources.txt
  expected_workbook.py     A requirements workbook that is also a test: every row has an Expected rung.
  fetch_corpus.py          Fetch the public L5X exports listed in eval/corpus_sources.txt into a folder, for tests/test_corpus.py.
  mutation.py              Mutation check for the behaviour comparator: break correct rungs on purpose and count how often the comparator notices.
  oracle_run.py            Stand-in "always-correct" model: run a test workbook with each row answered by its expected rung.
  README.md
  requests.yaml
  run.py                   Score a model on eval/requests.yaml by meaning, not text.
  structure.py             Write STRUCTURE.txt: every folder and file of the repository, each with one line on what it is.
  suite.py                 Instruction-coverage test suite: English requests with expected rungs.
  suite_run.py             Run the instruction suite and write a report.

explain/                   From existing logic to words and pictures: rungs back to LogicSpec, ladder drawings, rung comments.
  __init__.py
  comments.py              Write the plain-English read of each rung into the L5X as its rung comment.
  decompiler.py            Turn existing rungs back into LogicSpec.
  equivalence.py           Do two LogicSpec programs do the same thing?
  ladder.py                Draw a rung as a ladder diagram (SVG), the way Logix Designer lays it out: left and right power rails, contacts and coils as symbols, every other instruction as a box with its operands, branches as parallel legs, outputs pushed to the right rail.
  README.md
  survey.py                Survey a folder of L5X exports: does our parser, catalog and decompiler agree with real files? Used to confirm format details and find gaps.
generate/                  From what the user gives to LogicSpec or UDTs: the local model, its prompt and checks, and the Excel readers.
  __init__.py
  examples.yaml
  gbnf.py                  Per-request GBNF grammar (llama.cpp) for LogicSpec.
  iolist.py                An I/O list: every field signal, its tag, its address and what it is.
  llm/
    __init__.py            Plain English -> LogicSpec with a local model through Ollama.
    checks.py              Output checks that send the model back: unrequested latches, OR-splits, stray RISE, unnamed outputs.
    clients.py             Model clients: Ollama and OpenAI-compatible local servers (llama.cpp, LM Studio).
    generator.py           Request -> LogicSpec -> compiled rungs, with retries on any failed check.
    names.py               Tag names in requests and specs: what the user wrote, what the model wrote.
    prompt.py              The system prompt and the examples and tags each request is shown.
  README.md
  spec_excel.py            A requirements workbook: each sheet is one routine, each row one requirement (one or more rungs).
  udt_llm.py               Plain English -> UDT.

lint/                      The 50 programming rules (CRT/ERR/WAR/INF), the company profile, and auto-fix where a fix is certain.
  __init__.py              Static checks against a fixed checklist of PLC programming rules (CRT/ERR/WAR/INF codes).
  autofix.py               Fix what the lint finds, where a fix is certain, and say plainly what each fix changes.
  checks_io.py             Physical I/O rules: unmapped points, aliases, point comments, electronic keying.
  checks_lifecycle.py      Module lifecycle rules, from the catalog-number list in lifecycle.json.
  checks_logic.py          Rung rules: they need only the rungs and the tag types, so they also run on freshly generated logic.
  checks_project.py        Controller, task, program and AOI rules: they need the whole project.
  checks_tags.py           Tag rules: naming, data types, presets, usage, descriptions.
  checks_udt.py            Data type rules: padding, member order, unused definitions, member descriptions.
  context.py               Everything a rule needs, built once from a Project: rung list with locations, tag lookup by scope, operand types, operand roles from the instruction catalog.
  lifecycle.json
  paths.py                 Path questions on the rung AST (core.rung): what is guaranteed to run before an instruction on its power path, which sequences and branches a rung has.
  profile.py               A company coding-standards profile: rules that differ per company, checked like any other rule.
  README.md
  registry.py              Check functions register here with the codes they can emit.
  rules.py                 The rule checklist: codes, titles, descriptions, scope.
